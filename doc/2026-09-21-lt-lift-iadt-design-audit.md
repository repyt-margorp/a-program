## Problem

`LT.step 1` and `LT.lift 0 1 (LT.step 0)` carry the same endpoint proposition using different free-IADT constructor trees. Existing consumers inspect those trees, coupling partition construction history to accessibility and correctness evidence.

This does not show different sorted outputs, a false order relation, or a soundness failure. Constructor history may be an intentional semantic choice. The design should say whether LT represents an order fact or an observable derivation language.

# Design Audit: `LT` as an IADT and the Redundant `lift` Constructor

**Status:** Problem statement / design audit  
**Scope:** `pointer-core-hott` QuickSort, `LT`, `Acc`, `Partition`, and post-hoc Sorted proofs  
**Primary concern:** accidental proof relevance and representation coupling in the current `LT` encoding  
**Not a claim of:** a current soundness bug or an argument for introducing a separate `Prop` universe

---

## 1. Executive Summary

The current QuickSort provider defines natural-number strict order `LT` as an indexed algebraic data type with three constructors:

```text
LT :=
    @\left : Nat =>
    @\right : Nat =>
    {
        step : (n : Nat) -> * n (Nat.succ n);
        weakenRight : (m : Nat) -> (n : Nat) -> * m n ->
            * m (Nat.succ n);
        lift : (m : Nat) -> (n : Nat) -> * m n ->
            * (Nat.succ m) (Nat.succ n);
    };
```

At the level of inhabited indices, this still describes the intended strict order on natural numbers. The design concern is instead **intensional**: `step`, `weakenRight`, and `lift` are overlapping ways to construct the same indexed relation. In particular, `lift` is derivable from the relation generated by `step` and `weakenRight`, but is currently also admitted as a primitive constructor.

This creates multiple observably different constructor trees for the same fact. For example, both of the following inhabit `LT 1 2`:

```text
LT.step 1
```

and

```text
LT.lift 0 1 (LT.step 0)
```

That distinction is not merely latent. The current implementation pattern-matches on `LT` constructors in `accessibleSucc`, and the IADT evaluator selects branches by constructor position. The QuickSort partitioner also builds `lift` versus `weakenRight` according to the branch taken, so the `LT` witness carries part of the partition execution history into the termination evidence.

The concern is therefore **not that `LT` is an ordinary IADT**. An ordinary IADT is compatible with the Higher Observational Type Theory direction of A Program. The concern is that this particular free-IADT presentation introduces accidental proof-relevant structure that the mathematical relation does not appear to require.

A minimal experiment should remove `lift` as an `LT` constructor, reintroduce it as a derived theorem/function, and compare correctness, proof architecture, solver transitions, and graph/image size. This experiment does not require a separate `Prop` universe or global proof irrelevance.

### 2.2 `Partition` uses `lift` and `weakenRight` to record branch updates

A `Partition A bound` stores two size bounds:

```text
LT lowerSize (Nat.succ bound)
LT upperSize (Nat.succ bound)
```

When an element is sent to the lower partition, the implementation performs:

```text
(LT.lift lowerSize (Nat.succ size) lowerBound)
(LT.weakenRight upperSize (Nat.succ size) upperBound)
```

When an element is sent to the upper partition, the roles reverse:

```text
(LT.weakenRight lowerSize (Nat.succ size) lowerBound)
(LT.lift upperSize (Nat.succ size) upperBound)
```

Current source locations: lines 95–125.

Source:
<https://github.com/repyt-margorp/a-program/blob/rewrite/pointer-core-hott/src/prototype/pointer/tests/fixtures/sorted-proof-provider.p#L95-L125>

Therefore the constructor spine of the bound witness is correlated with the sequence of partition decisions. A `lift` node means that the corresponding side grew at that step; a `weakenRight` node means that only the global bound grew.

For a partition process with `N` decisions and final lower size `l`, there are `binomial(N, l)` possible lower/upper decision sequences with the same final sizes. The current construction can preserve those different histories as different `LT` constructor trees even though the final order fact is the same.

This is the first concrete representation leak:

```text
partition decision history
        ↓
LT constructor history
```

## 3. Why Higher Observational Type Theory Does Not Automatically Remove This Concern

This audit is **not** based on a Lean/Coq-style assumption that propositions must live in a special proof-irrelevant `Prop` universe.

A Program is explicitly pursuing Higher Observational Type Theory, and it is reasonable for relations such as `LT m n` to remain ordinary types/IADTs.

The relevant implementation fact is narrower: the current system does not globally identify arbitrary inhabitants merely because an Identity witness exists.

The README states that:

> Identity witnesses do not extend global definitional equality or change interning.

See `README.md`, implementation model, around lines 103–125:

<https://github.com/repyt-margorp/a-program/blob/rewrite/pointer-core-hott/README.md#L103-L125>

The README also describes the current Higher Identity support as selected typed action/transport/higher-dimensional examples, with general coherence still unfinished:

<https://github.com/repyt-margorp/a-program/blob/rewrite/pointer-core-hott/README.md#L146-L160>

Therefore this audit should not assume that the following two terms are automatically collapsed by the current Higher Observational machinery:

```text
LT.step 1
```

```text
LT.lift 0 1 (LT.step 0)
```

If the intended semantics eventually identifies all inhabitants of each `LT m n`, that identification would itself require an explicit higher/observational design and associated coherence. The question raised here is whether that machinery should be required merely to erase redundancy introduced by the definition of natural-number order.

## 5. Precise Problem Statement

The problem is **not**:

> `LT` is an IADT, therefore it should be changed into `Prop`.

The problem is:

> The current free-IADT presentation of `LT` contains overlapping introduction rules. In particular, `lift` is both derivable from the order generated by `step` + `weakenRight` and admitted as a separate constructor. This creates accidental derivation structure that is subsequently observed by `Acc` and reproduced by Sort correctness proofs.

Equivalently:

```text
mathematical information wanted:
    m < n

current evidence may additionally contain:
    how this inequality was built
    + which partition updates generated it
```

The second component does not currently appear to be part of the intended semantic content of `LT`.

---

## 6. `lift` Is Not Inherently Wrong as a Constructor

This distinction is important.

There are multiple valid inductive presentations of natural-number strict order. A lift/successor rule can perfectly well be a primitive constructor in a **non-overlapping** presentation.

For example, one could choose a presentation roughly of the form:

```text
base : LT Nat.zero (Nat.succ n)
succ : LT m n -> LT (Nat.succ m) (Nat.succ n)
```

and derive right weakening as a theorem.

Alternatively, the current code is already close to another canonical presentation:

```text
step : LT n (Nat.succ n)
weakenRight : LT m n -> LT m (Nat.succ n)
```

and `lift` can then be derived as a theorem.

The concern is therefore **not the name or mathematical validity of `lift`**. The concern is simultaneously having:

```text
step
weakenRight
lift
```

when one of these introduction principles is derivable from the others and creates alternative constructor trees for the same indices.

For the current `Acc` implementation, the `step + weakenRight` presentation appears especially natural because elimination of:

```text
LT y (Nat.succ current)
```

then decomposes directly into:

1. `y = current` (`step`), or
2. `y < current` (`weakenRight`).

This matches exactly what `accessibleSucc` needs.

## 7. Proposed Minimal Refactor Experiment

### 7.1 Keep `LT` as an ordinary IADT

No separate `Prop` universe is required by this proposal.

Use:

```text
LT :=
    @\left : Nat =>
    @\right : Nat =>
    {
        step : (n : Nat) -> * n (Nat.succ n);
        weakenRight : (m : Nat) -> (n : Nat) -> * m n ->
            * m (Nat.succ n);
    };
```

### 7.2 Reintroduce lifting as a derived theorem/function

Conceptually:

```text
ltLift :
    (m : Nat) ->
    (n : Nat) ->
    LT m n ->
    LT (Nat.succ m) (Nat.succ n)
```

with recursion on the existing `LT` evidence.

Schematic implementation:

```text
ltLift := \m : Nat => \n : Nat => \p : LT m n =>
    p
        @step k =>
            LT.step (Nat.succ k)
        @weakenRight a b prior =>
            LT.weakenRight
                (Nat.succ a)
                (Nat.succ b)
                *prior;
```

The exact accepted surface syntax should be validated against the current pointer prototype; this snippet states the intended construction rather than claiming to be a tested patch.

### 7.3 Update Partition

Replace:

```text
LT.lift ... bound
```

with:

```text
ltLift ... bound
```

The partition algorithm still obtains exactly the inequality it needs, but `lift` no longer adds a new derivation form to the relation.

### 7.4 Simplify `accessibleSucc`

The intended eliminator becomes conceptually:

```text
edge
    @step k => proof
    @weakenRight m k prior => down m prior
```

The `@lift` bookkeeping branch disappears.

### 7.5 Update post-hoc proofs

`lower_all`, `upper_all`, `partition_all`, and `partition_ordered` should use the derived `ltLift` theorem rather than reproducing a primitive `LT.lift` constructor.

## 8. What This Refactor Would and Would Not Establish

### It would establish

- `lift` does not need to be an independent constructor for the current Sort/Acc use case.
- the current QuickSort termination proof can potentially operate on a less proof-relevant order representation;
- `accessibleSucc` can potentially match the mathematical predecessor decomposition more directly;
- correctness proofs can depend on an order theorem rather than a particular primitive representation;
- some partition execution history can be prevented from leaking into `LT` evidence.

### It would **not** by itself establish

- that every `LT m n` is observationally a proposition in the full Higher Observational Type Theory sense;
- that all inhabitants are definitionally equal;
- that a global proof-irrelevance principle should exist;
- that the current implementation is unsound;
- that removing the constructor necessarily improves runtime or solver performance.

Those are separate questions.

---

## 9. Canonicality / Higher-Structure Question to Test Separately

After removing the overlapping constructor, a useful design goal is to ask whether each fiber:

```text
LT m n
```

has the intended observational truncation level.

For closed natural-number indices, `step + weakenRight` gives an evidently much more canonical raw constructor shape: once `m` and `n` are fixed, the right index determines how many `weakenRight` layers occur before `step`.

However, the stronger statement that `LT m n` is proposition-like under A Program's eventual Higher Observational equality should be **proved/tested separately**, rather than assumed from this refactor.

This separation is desirable:

1. avoid generating unnecessary derivation multiplicity at the IADT level;
2. then characterize the actual higher/observational structure of the resulting type.

This is preferable to intentionally generating redundant proof history and relying on higher coherence machinery to quotient it away later, unless that redundancy has a semantic purpose.

---

## 10. Performance Trade-off: Do Not Assume the Refactor Is Free

There is one important counterargument to removing primitive `lift`.

As a constructor:

```text
LT.lift ... prior
```

adds one node in constant local construction time.

As a derived recursive theorem, `ltLift` may traverse and rebuild an existing `LT` derivation. With the `step + weakenRight` representation, that work is proportional to the distance represented by the witness.

Therefore there is a genuine trade-off:

```text
primitive lift:
    cheap local construction
    but more derivation forms / more representation leakage

 derived ltLift:
    more canonical relation structure
    but potentially more proof reconstruction work
```

This must be measured rather than guessed.

Possible mitigations, if reconstruction is expensive, should be considered only after measurement. Examples could include sharing/memoization, a different canonical representation of `<`, or proof erasure/observational optimization. Reintroducing overlapping constructors should not be the first optimization without understanding the graph-level cost.

## 12. Decision Criteria

Retaining primitive `LT.lift` should require at least one explicit justification beyond convenience, for example:

1. the derivation history is intentionally semantic and should be observable;
2. Higher Observational equality is intended to identify the alternative derivations, and the required coherence is part of the design rather than accidental debt;
3. benchmark evidence shows that a canonical alternative is prohibitively expensive and no representation-neutral optimization is viable;
4. `LT` is intentionally a derivation object rather than merely the strict-order relation.

If none of these is intended, a derived `ltLift` is the cleaner default.

---

## 13. Recommended Interpretation of the Current State

The current implementation should not be described as "wrong `<`" or as a soundness failure.

A more precise description is:

> `LT` currently conflates the strict-order relation with a derivation language containing a redundant introduction rule. QuickSort's partitioning and accessibility machinery expose that derivation language operationally, causing algorithmic construction history to leak into termination and correctness evidence.

This is an architectural concern because A Program is building a system in which ordinary indexed types, explicit evidence, function graphs, and Higher Observational identity all interact. Redundant free-IADT structure therefore has consequences beyond cosmetic proof style.

---

## 14. Proposed Next Action

Implement a **parallel experimental provider** with:

```text
LT = step + weakenRight
ltLift = derived theorem
```

without modifying the existing baseline fixture first.

Then run the same QuickSort and universal Sorted workloads against both providers and record:

```text

- accepted/rejected
- solver transitions
- graph nodes/edges
- `.a` image size
- memory
- wall-clock
- proof source size

```

Only after this A/B comparison should the repository decide whether `lift` remains a primitive constructor.

## 16. Short Issue Version

For a GitHub issue or review comment, the concern can be summarized as follows:

> `LT` currently has `step`, `weakenRight`, and `lift` as primitive IADT constructors. `lift` appears derivable from `step + weakenRight`, so the three-constructor presentation creates multiple constructor trees for the same strict-order fact.
