# Path Equality, Quotients, and Intrinsic Semantic Models

Date: 2026-08-06

Status: design problem statement and pre-implementation migration plan. No
object-language equality, quotient, or intrinsic semantic-model feature is
approved by this document alone. The target equality family is Higher
Observational Type Theory; the exact calculus and its initial executable
fragment remain to be specified before code changes begin.

## 1. Purpose

The immediate request that exposed this problem was small:

```text
#.Int -> #.Text
```

The current prototype can add another host-backed pure primitive with this
classifier. That implementation would be type-safe at the existing primitive
boundary, but its meaning would remain external to A Program. The language
would know only that an opaque term of one host type produces an opaque term of
another host type. It could not state, calculate, or verify why the output is
the canonical decimal representation of the input.

The intended system needs a stronger boundary:

1. machine representations such as 32-bit words have an A Program-visible
   semantic model;
2. operations on those representations are related to model operations by
   explicit laws;
3. a host implementation is an optimized realization of the model, not the
   authority that silently defines the model;
4. equality used to state and verify those laws is not confused with kernel
   definitional conversion;
5. compiler optimization, type checking, automatic proof, and artifact
   validation share proof and constraint infrastructure without sharing one
   mutable global equivalence relation.

This document records how the discussion reached that requirement, identifies
the current implementation gaps, and defines the work that must precede any
Equality implementation.

## 2. Original Objective and Why It Expanded

### 2.1 The missing conversion

The prototype currently exposes host types including:

```text
#.Text
#.Int / #.Int32
#.Int64
```

It also exposes pure primitives such as integer addition and negation. There is
no pure primitive for converting an integer value to text.

The first implementation idea was:

```text
#.int_to_text : #.Int -> #.Text
```

internally classified, under the current CBPV convention, as approximately:

```text
Pi(#.Int, Comp({}, #.Text))
```

This remains a useful executable operation, but adding only that declaration
does not explain its semantics inside A Program.

### 2.2 Why an opaque function type is insufficient

The following facts are absent from a bare `#.Int -> #.Text` classifier:

- whether `#.Int` is signed, unsigned, fixed-width, or target-width;
- whether arithmetic wraps, traps, saturates, or is undefined on overflow;
- whether decimal rendering is canonical and locale-independent;
- whether `#.Text` denotes Unicode scalar sequences, UTF-8 bytes, or a host
  string object;
- whether the operation is total and deterministic;
- whether the operation may participate in kernel conversion;
- which equations a proof or optimizer may rely on;
- whether two backend implementations realize the same semantics.

Calling this merely an opaque positive datatype is not adequate. Opacity,
strict positivity, proof relevance, purity, linearity, and implementation
trust are separate properties. A future quantum value may also be opaque, but
its copying, measurement, and effect rules differ fundamentally from a machine
word.

### 2.3 The representation-bridge problem

The discussion therefore moved from one formatting primitive to a family of
representation bridges:

```text
machine carrier <-> constructive model
character value <-> scalar-value model
text value      <-> character-sequence model
text value      <-> encoded-byte model
```

The bridge must carry laws. A function signature alone does not establish a
retraction, injection, quotient law, encoding law, or backend refinement.

## 3. The UInt32 Semantic Model

### 3.1 UInt32 is not a 2^32-constructor Match

A finite type with `2^32` inhabitants does not require a declaration with
`2^32` point constructors. Useful equivalent set-level presentations include:

```text
Fin(2^32)
BitVec(32)
Nat modulo congruence generated by 2^32 == 0
```

Each presentation emphasizes different operations:

| Presentation | Natural structure |
| --- | --- |
| `Fin(2^32)` | canonical unsigned representative and order |
| `BitVec(32)` | bitwise operations, shifts, and hardware layout |
| `Nat/(2^32 == 0)` | cyclic addition, multiplication, and wraparound |

The quotient presentation is especially relevant to A Program because it
allows Nat-like generation and elimination while making modular arithmetic an
explicit equation of the model.

### 3.2 The required quotient is a congruence quotient

A bare path between two embedded points is insufficient:

```text
embed(2^32) == embed(0)
```

By itself, this does not define all expected periodic equations unless the
successor/algebra structure and its congruence closure are also part of the
definition. A set-level formulation is:

```text
Congruent32(a, b) := a mod 2^32 == b mod 2^32
UInt32Model       := SetQuotient(Nat, Congruent32)
```

An algebraic quotient-inductive presentation is conceptually:

```text
zero  : UInt32Model
succ  : UInt32Model -> UInt32Model
wrap  : iterate(succ, 2^32, zero) == zero
trunc : isSet(UInt32Model)
```

The `trunc` requirement matters. Without local zero-truncation, the path
constructor may generate proof-relevant higher structure that is not part of
the ordinary machine-word model.

### 3.3 Elimination is Nat elimination plus periodicity

To define a function from this cyclic type into a set `X`, it is not enough to
provide a Nat recursion. The result must respect the quotient:

```text
x0       : X
step     : X -> X
periodic : iterate(step, 2^32, x0) == x0
```

Equivalently, for a quotient recursor:

```text
f        : Nat -> X
respects : Congruent32(a, b) -> f(a) == f(b)
```

This restriction is essential. Raw Nat order does not descend directly to the
quotient because `0 < 2^32` but the two values represent the same residue.
Unsigned comparison first chooses canonical representatives. Bitwise
operations use the equivalent bit-vector view.

### 3.4 DefEq must not orient the wrap equation both ways

The proposition/path:

```text
2^32 == 0
```

must not become an unrestricted global conversion equation. An unoriented
DefEq rule could expand indefinitely:

```text
0 == 2^32 == 2 * 2^32 == ...
```

Executable normalization must choose a canonical direction, such as:

```text
n -> n mod 2^32
```

The path proving wraparound and the normalizer implementing canonicalization
are related but distinct objects.

### 3.5 Signed and unsigned views

`UInt32` and `Int32` may share the same erased 32-bit carrier. They do not have
the same public interpretation:

```text
unsigned : Word32 -> Fin(2^32)
signed   : Word32 -> Z
```

Signed comparison, division, and text formatting depend on the signed view.
Unsigned operations depend on the canonical non-negative representative. This
is consistent with the existing Core/TypeView distinction: representation
sharing does not imply source type identity or conversion.

## 4. Text, Characters, and Encoding

The semantic model must distinguish at least:

```text
CharModel   := a valid character scalar value
TextModel   := a sequence of CharModel
Byte        := a finite 8-bit word
EncodedText := a sequence of Byte under a selected encoding
```

A character scalar is not one UTF-8 byte. The following bridges have different
meanings:

```text
char_to_scalar   : CharModel -> UInt32Model
char_from_scalar : UInt32Model -> Option(CharModel)

encode_utf8 : TextModel -> List(Byte)
decode_utf8 : List(Byte) -> Result(DecodeError, TextModel)
```

The desired formatting model is then a composition:

```text
UInt32Model
  -> canonical Nat representative
  -> decimal digits
  -> CharModel sequence
  -> TextModel
```

For signed formatting, the first step uses the signed interpretation and a
constructive integer model. A host implementation may fuse this composition,
but the fused implementation must not become the only specification.

## 5. Five Equality Relations That Must Remain Distinct

### 5.1 Exact TermDB identity

If two references contain the same valid TermDB ID in the same database, they
refer to the same canonical Core node. Kernel conversion must be reflexive on
that node even if normalization would be blocked or recursively guarded:

```text
t DefEq t
```

The current `classifier_kernel_normalization_equal(...)` implements this
short path before normalization.

This rule must be stated with its layer and context. Two OperationGraph
occurrences may point to the same Core node while carrying different public
classifiers or TypeViews. Exact Core identity does not erase occurrence-level
typing distinctions.

### 5.2 Definitional or judgemental equality

Distinct TermDB nodes may still be DefEq when the fixed kernel normalization
profile computes them to equal results:

```text
APP(LAMBDA(x, body), value) DefEq body[x := value]
```

In the current prototype this is a meta-level decision procedure implemented
through `prototype_term_normalization_equal_with_profile(...)`, normally with
`PURE_TYPE_WHNF` for classifier conversion.

DefEq depends on the selected fixed kernel calculus and transparency policy.
It must not depend on imported user equality proofs, optimizer search order,
runtime handlers, host effects, or machine speed.

### 5.3 Structural and representation equality

The current TermDB has separate comparison APIs for view shape, Core shape,
and source shape. These are useful for interning, representation sharing,
readback, and artifact validation. They are not object-language equality
witnesses and must not be accepted as typed conversion by accident.

### 5.4 Propositional or path equality

The intended object language needs terms whose classifiers state endpoint
equality:

```text
p : Path(A, lhs, rhs)
```

This is a first-class term and belongs in the object-language term vocabulary.
Its typing derivation belongs in JudgementDB. The fact that the kernel can
check `p` must not mutate global DefEq:

```text
p : Path(A, lhs, rhs)
does not imply
lhs DefEq rhs
```

Movement along `p` is explicit transport, coercion, or rewrite at a selected
occurrence.

### 5.5 Optimization and representation evidence

A compiler may prove that one implementation refines another and use that
proof to rewrite a selected graph occurrence. This evidence is neither DefEq
nor necessarily an ordinary user-facing path:

```text
source implementation
rewrite theorem and side conditions
proof/certificate
target implementation
```

An e-graph may index candidate equalities, but each selected extraction edge
must retain its justification. User PropEq proofs must not be inserted into a
global DefEq union-find.

## 6. Current Layer Ownership

### 6.1 TermDB

TermDB is the canonical static computation and classifier graph. It currently
contains Core terms, CBPV boundaries, type views, host values, pure primitives,
effect operations, and operation requests. Pure normalization may add
canonical result nodes.

TermDB currently has no object-level equality type, equality constructor,
transport, path abstraction, dimension variable, face constraint, composition,
set quotient, or path constructor.

### 6.2 OperationGraph

OperationGraph owns elaborated source occurrences and their contexts,
classifiers, polarity, provenance, and solver edges. Multiple occurrences may
point to one TermDB node.

Future equality syntax must initially produce an OperationGraph occurrence. It
must not be lowered directly to an uncontextualized pair of TermDB IDs, because
the endpoints may use local binders, public TypeViews, and occurrence-specific
classifier evidence.

### 6.3 ContextDB and SubstitutionDB

The current CwF-oriented context and substitution structures are the natural
home for endpoint context, weakening, reindexing, and ordinary substitution.
They do not yet represent a cubical dimension context, face lattice, path
endpoint substitution, or composition data.

### 6.4 JudgementDB

JudgementDB currently records only `HAS_TYPE` and `IS_TYPE` relations. Its
`CONVERSION` proof kind means:

```text
subject : actual
actual DefEq expected
---------------------
subject : expected
```

The conversion premise is validated by the meta-level normalizer. It is not a
first-class equality proof and has no term that users can abstract over,
return, match, transport with, or serialize as an equality witness.

The conversion implementation also contains defensive compression of chains
of conversion derivations. That proof-DAG maintenance must remain distinct
from path composition in the object language.

### 6.5 Constraint solvers

The OperationGraph classifier solver currently has specialized equations for
classifier variables, Match motives, IH applications, constructor spines, and
effect rows. Its candidate equality is compiler-local state and is not a
general typed equation language with proof-producing solutions.

Range constraints, bit-vector constraints, quotient-respect obligations, and
representation-refinement obligations do not yet share one explicit
certificate-bearing constraint IR.

### 6.6 VerificationDB and artifacts

Residual verification records exist for selected dependent-CBPV cases and
bounded static work. There is no general residual proposition/path obligation
format, no serialized equality proof term, and no artifact contract for
replaying quotient or primitive-refinement evidence.

### 6.7 Runtime machine

Runtime state remains separate from TermDB. Equality proofs that are
computationally irrelevant may eventually be erased, but erasure is a typed
compiler decision. The Core must not identify all path proofs merely because a
backend erases them.

## 7. Current Implementation Gaps and Refactoring Needs

### 7.1 No selected equality kernel

The prototype has not selected among:

```text
intensional identity with Eq/refl/J
cubical path equality with dimensions and composition
higher observational equality with level-sensitive observations
```

Adding an `EQ` tag before this decision would let incidental C data structures
choose the theory. This is the first design gate.

### 7.2 Conversion is centralized semantically but scattered operationally

Classifier conversion ultimately delegates to the pure normalization equality
entry point, which is good. However, `typing.c` contains many direct callers and
specialized list/search helpers that repeatedly invoke normalization equality.

Before adding object equality, the code needs a single kernel conversion
service returning a structured result rather than a bare boolean. Its result
must distinguish at least:

```text
reflexive same-node
complete normalization equality
complete inequality
blocked
budget exhausted
invalid
```

It should optionally retain replayable evidence or a normalized-result claim.
Object Path construction must not call scattered private equality helpers.

### 7.3 Judgement proof records do not represent equality conclusions

`prototype_judgement_kind` has no equality judgement, and proof conclusions
have only `subject` and `classifier`. This is sufficient for has-type proofs,
including conversion, but not sufficient for a separate meta-level equality
derivation if one is desired.

This does not imply that PropEq itself belongs as a new JudgementDB relation:
an object-level `p : Path(A, x, y)` remains an ordinary has-type judgement.
The design must decide whether the kernel also stores a replayable meta-level
conversion derivation distinct from the object proof term.

### 7.4 Structural equality APIs need stronger naming and ownership

The current `core_shape_equal`, `view_shape_equal`, and `source_shape_equal`
APIs are deliberately different, but equality implementation will increase the
risk that one is reused as conversion or Path evidence. Their contracts must
state accepted callers and whether they preserve binders, contexts, public type
identity, and cross-artifact identity.

### 7.5 Primitive declarations have no semantic model

`prototype_pure_primitive_declaration` currently stores only:

```text
primitive id
arity
host argument type ids
host result type id
```

Host implementation dispatch separately maps a primitive id to an oracle kind.
There is no field for:

```text
semantic model term
representation relation
correctness theorem/certificate
semantic version
backend implementation identity
allowed normalization profiles
```

Consequently, `PURE_PRIMITIVE` currently means a typed deterministic host
reduction contract, not a verified refinement of an A Program definition.

### 7.6 Host types lack constructive views

The current host-type set contains Text, Int32, and Int64. It lacks at least:

```text
UInt32 / Word32
Byte
Char
an explicit constructive representation bridge
```

Adding these names alone would repeat the same problem. Each host carrier needs
a semantic-model relation, not just another type tag.

### 7.7 Text and integer formatting are underspecified

The current Text host type and text literal representation do not establish an
A Program-level character sequence or external byte encoding. Integer
formatting cannot be proved correct until the target Text model is fixed.

The specification must fix signedness, radix, canonical leading-zero policy,
minus-sign policy, locale independence, scalar repertoire, and encoding
boundary.

### 7.8 Solver evidence is not yet general enough

The planned automatic proof system requires explicit constraints such as:

```text
range(x) is within Int32
bitvector expression lhs equals rhs
function respects quotient relation
backend operation refines model operation
```

The current classifier/effect fixed-point is not this proof system. It may be
reused as worklist infrastructure, but its specialized mutable bindings must
not become the universal representation of propositions.

### 7.9 Artifact identity does not identify primitive semantics

Artifacts distinguish pure primitive and effect-operation tags, but a stable
primitive id or source spelling alone does not prove that two compiler builds
assign the same semantics. A future artifact boundary needs a semantic model
hash/version and verifier requirements.

### 7.10 Current pure-intrinsic exclusion from DefEq is correct

The current reduction flags explicitly keep deterministic host intrinsics
available to execution and unavailable to pure type conversion. This boundary
must remain until a primitive has an accepted semantic model and the kernel has
a deterministic, replayable rule for using it.

Even after refinement proofs exist, runtime implementation execution should not
automatically become DefEq. The kernel may compute the model, validate a
certificate, or keep the application opaque.

## 8. Where Object-Level Path Terms Belong

The tentative ownership rule is:

```text
TermDB:
  Path/Eq type terms, equality proof terms, transport terms, and eventually
  quotient/path constructors as object-language computation

OperationGraph:
  source occurrences, endpoint contexts, expected classifiers, elaboration
  choices, and generated equality constraints

JudgementDB:
  proofs that Path terms and transport terms are well typed

Kernel conversion service:
  fixed judgemental equality; never extended by arbitrary Path inhabitants

Constraint/Verification layer:
  proof search, certificates, residual obligations, and optimizer side
  conditions

Runtime:
  erased or executable representation selected only after typing
```

This rule is necessary but not sufficient. If cubical equality is selected,
TermDB and ContextDB also need dimension-indexed syntax and composition. If
intensional equality is selected, `refl` and `J` need their own computation
rules. If higher observational equality is selected, proof levels and
observations cannot be collapsed to a first-order equality tag.

## 9. Equality-Kernel Options

### 9.1 Intensional identity plus primitive set quotient

This option introduces `Eq`, `refl`, `J/transport`, and a separately checked
set quotient recursor. It has the smallest immediate kernel delta.

Risk: it must not be described as a conservative path to computational
cubical equality without a translation and computation argument. A primitive
quotient may also hide precisely the computation that the project wants to
make explicit.

### 9.2 Cubical path foundation

This option treats paths as dimension-indexed terms and gives transport and
higher inductive types computational content. It aligns most directly with the
long-term homotopic objective.

Cost: dimension contexts, endpoint substitution, face constraints,
composition/coercion, canonicity-sensitive normalization, and artifact support
become kernel concerns. It is not an `Eq`-tag-only feature.

Decision: do not use Cubical Path as the A Program kernel foundation. Cubical
systems remain important reference models for computational higher equality,
HIT behavior, and validation examples, but A Program will not expose an
interval and Kan-composition machinery merely to obtain those results.

### 9.3 Higher observational equality

This option makes equality type-directed and level-sensitive. It may fit the
project's insistence that typed observations, not raw representation shape,
determine equality.

Cost: the exact calculus, computation rules, universe interaction, and
preservation of higher witnesses must be selected before implementation. A
generic `OBS_EQ` node without this structure would not implement the theory.

Decision: this is the target equality foundation. Equality is intended to be
calculated structurally from each type former and preserved at higher levels,
without making an explicit interval the source-language or Core explanation of
equality. This direction matches A Program's existing emphasis on typed
observations, TypeViews, contexts, substitutions, and type-former-specific
elimination.

This decision is based on internal fit, not on whether another implementation
or publication has already stabilized every rule. A Program has already
entered a research area in which its combination of graph sharing, TypeViews,
dependent CBPV, algebraic effects, staged verification, and intrinsic semantic
models is not supplied by one existing calculus. The project must therefore
formulate and validate the concrete observational theory it implements.

This is a theory-first requirement, not permission to experiment in code until
an implementation appears to work. The required order is:

```text
semantic commitments
  -> formal syntax and judgements
  -> equality and computation rules
  -> substitution, subject-reduction, canonicity, and consistency obligations
  -> graph-layer ownership and artifact invariants
  -> kernel data structures and implementation
```

Prototype code may test an already stated rule or expose a counterexample. It
must not silently define the rule by whatever behavior is convenient in C.

Existing Higher Observational and Cubical work supplies constraints,
counterexamples, models, and comparison tests. It does not replace the need to
specify observational equality rules for A Program's actual type formers,
including Pi, inductive types, CBPV computation types, thunks, effects,
universes, and the intended quotient model. Definitional univalence or higher
structure may be claimed only when those selected rules and their metatheory
establish it, not merely because the project uses the Higher Observational
name.

### 9.4 Opaque equality axioms

This option would postulate quotient laws and primitive correctness without a
computational eliminator or checked model.

Decision: reject as the target design. It reproduces the current intrinsic
problem at the equality layer. Temporary axioms may be useful in isolated
experiments only when artifacts expose the resulting assumptions.

## 10. Intrinsic Semantic Contracts

The target intrinsic architecture has three categories.

### 10.1 Defined operation

The operation and its model are ordinary A Program terms.

```text
uint32_to_text_model : UInt32Model -> TextModel
```

### 10.2 Refined primitive

The operation has an optimized host implementation and a model relation:

```text
decode_text(host_uint32_to_text(encode_uint32(x)))
  == uint32_to_text_model(x)
```

The primitive declaration references the model, representation relation, and
proof/certificate policy.

### 10.3 Opaque effect operation

Operations such as terminal output, file access, clocks, or quantum
measurement interact with an external system. They have operation contracts
and effects rather than a claim that host execution is a pure implementation
of one closed term.

This division keeps pure primitive reduction separate from algebraic effect
requests while preventing pure primitives from being semantically anonymous.

## 11. Automatic Proof, Type Checking, and Optimization

The same proof infrastructure should support different producers without
turning their results into global DefEq:

```text
OperationGraph
  -> constraint generation
  -> typed constraint IR
  -> bounded solver/proof search
  -> proof term or certificate
  -> small checker
  -> selected typing, transport, or optimization result
```

Constraint classes will eventually include:

```text
classifier equations
effect-row constraints
universe constraints
integer range constraints
bit-vector equations
quotient-respect obligations
representation-refinement obligations
```

Machine-dependent lowering illustrates the distinction:

```text
x + y : Z
```

may be replaced by Int32 addition only after proving the required range and
overflow policy. A term already typed as wrapping `UInt32` needs no such range
proof for modular addition because wrapping is its source semantics.

Solver budgets may change how many obligations are discharged, but an artifact
must record proof/certificate status and residual obligations. Budget variation
must not silently change the fixed DefEq calculus.

## 12. Pre-Implementation Migration Plan

### Phase 0: Freeze terminology and invariants

- [x] Record the five equality relations in this document.
- [x] Record that same TermDB ID implies reflexive DefEq only at the relevant
      Core/context layer.
- [x] Record that user Path proofs never extend global DefEq.
- [x] Record that intrinsic implementations need A Program-visible semantic
      models.
- [x] Select Higher Observational Type Theory as the intended equality
      foundation.
- [ ] Specify the concrete higher observational calculus and the finite first
      kernel fragment before adding surface syntax or Core tags.

### Phase 1: Audit and centralize kernel conversion

- [ ] Inventory every caller of classifier normalization equality, structural
      shape equality, and conversion-proof construction.
- [ ] Replace boolean-only internal conversion results with one structured
      outcome API.
- [ ] Make normalization profile, transparency environment, context, budget,
      and evidence ownership explicit in that API.
- [ ] Ensure only complete kernel outcomes justify JudgementDB conversion.
- [ ] Add regression tests proving runtime pure primitives and effects cannot
      alter conversion.

### Phase 2: Separate equality evidence schemas

- [ ] Specify the representation of meta-level conversion evidence.
- [ ] Specify the representation of object-level Path terms.
- [ ] Specify optimizer/refinement certificates separately.
- [ ] Decide which evidence is serialized, replayed, recomputed, or erased.
- [ ] Remove or rename helpers whose generic `equal` wording crosses these
      ownership boundaries.

### Phase 3: Generalize constraint and residual infrastructure

- [ ] Define a typed constraint IR independent of classifier-solver mutable
      cells.
- [ ] Give each solved constraint a proof term or checkable certificate.
- [ ] Add explicit residual proposition obligations to VerificationDB.
- [ ] Serialize solver policy, proof roots, residuals, and verifier version.
- [ ] Keep unresolved arbitrary conversion as rejection unless a selected
      residual rule gives it runtime meaning.

### Phase 4: Redesign pure primitive declarations

- [ ] Separate source namespace binding, semantic declaration, and backend
      implementation registry.
- [ ] Add semantic model identity/hash and version.
- [ ] Add representation-domain and representation-codomain relations.
- [ ] Add correctness evidence policy and allowed reduction profiles.
- [ ] Reject artifact linking when primitive semantic contracts disagree.

### Phase 5: Prototype the selected equality core

- [ ] Implement only under `src/prototype/`.
- [ ] Add object terms and context support required by the selected theory.
- [ ] Add typing rules and independent proof validation.
- [ ] Add transport/rewrite without equality reflection.
- [ ] Test proof relevance at types not known to be sets.
- [ ] Test local `isSet` behavior without globally imposing UIP.

### Phase 6: Constructive machine and text models

- [ ] Add ordinary library models for `Bit`, `Fin`, bounded words, characters,
      text sequences, bytes, and encodings as supported by the selected core.
- [ ] Define `UInt32Model` using a set quotient or an equivalent proved model.
- [ ] Prove equivalences among cyclic, Fin, and bit-vector views.
- [ ] Define unsigned and signed interpretations separately.
- [ ] Define canonical decimal formatting into `TextModel`.

### Phase 7: Refine host primitives against the models

- [ ] Introduce `#.UInt32` rather than using signed `#.Int` as the sole carrier.
- [ ] Relate host Word32, Int32, Char, and Text values to their models.
- [ ] Implement host formatting only after its canonical semantics are fixed.
- [ ] Verify closed examples against model evaluation.
- [ ] Preserve the model implementation as a fallback/reference evaluator.

### Phase 8: Proof-producing lowering and optimization

- [ ] Add guarded rewrite rules from model computations to host primitives.
- [ ] Add range and bit-vector proof producers with small certificate checkers.
- [ ] Retain justification on each selected optimization edge.
- [ ] Ensure e-graph saturation never mutates kernel DefEq.
- [ ] Record residual and completed optimization evidence in artifacts.

## 13. Required Tests Before Equality Is Considered Stable

### DefEq boundary

- exact same TermDB node is reflexively convertible;
- distinct beta/iota redexes convert under the fixed profile;
- shared Core with different TypeViews does not imply public type conversion;
- shape equality never acts as conversion evidence;
- runtime primitive execution and effect handlers cannot alter DefEq;
- exhausted normalization does not report inequality or equality.

### Object equality

- `refl` or the selected path introduction is well typed;
- transport changes a selected dependent occurrence without adding a global
  rewrite rule;
- two object proofs are not merged unless the endpoint type is proved to be a
  proposition/set at the required level;
- artifact round-trip preserves endpoints, context, and proof identity.

### Quotient model

- quotient elimination accepts a relation-respecting function;
- it rejects a non-periodic function such as raw Nat comparison;
- canonical unsigned representatives are unique;
- modular addition agrees in quotient, Fin, and bit-vector views;
- path witnesses do not become runtime word payload.

### Intrinsic refinement

- host UInt32 formatting agrees with the model at zero, powers of ten,
  maximum UInt32, signed boundaries, and negative signed values;
- locale and backend do not change canonical text;
- corrupted model hashes, implementation ids, or certificates are rejected;
- an unmodeled primitive remains explicitly opaque and unavailable to proof
  conversion or verified optimization.

## 14. Non-Goals of the First Equality Milestone

The first milestone must not claim all of the following automatically:

- full univalence;
- general higher inductive types;
- arbitrary quotient-inductive-inductive types;
- equality reflection;
- automatic promotion of user proofs to optimizer rules;
- verified C, Verilog, runtime, and hardware implementations;
- quantum-state semantics from the ordinary opaque-host-type mechanism;
- target-dependent `#.Int` behavior without an explicit target model.

The purpose of the first milestone is to establish a kernel boundary that does
not prevent those directions while making its actually implemented theory
precise.

## 15. Open Decisions

1. What exact Higher Observational Type Theory calculus is the long-term
   kernel, and what finite fragment is implemented first?
2. Is set quotient an observational type former with dedicated equality and
   elimination rules, or a construction derived from more general higher
   observational machinery?
3. Which observational equality computations are definitional and which remain
   witnessed propositional/higher equalities?
4. How do TermDB, ContextDB, and substitution represent level-sensitive
   observational witnesses and telescope structure without collapsing them to
   one first-order `OBS_EQ` node?
5. What is the exact semantic model of `#.Text`: Unicode scalar sequence,
   another abstract sequence, or a parameterized encoding-aware type?
6. Is `#.Int` permanently an alias of `#.Int32`, or should target-sized words
   receive a separate nominal type?
7. Which proof certificate formats are small enough for independent artifact
   validation?
8. How are backend refinement assumptions exposed when no complete proof is
   available?

No implementation of `==`, `refl`, Path, quotient, or verified
`#.int_to_text` should begin until at least decisions 1 through 4 have a
written answer.
